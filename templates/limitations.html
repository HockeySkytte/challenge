Limitations
What this data cannot answer, and what a production version would change

Three limits worth knowing before reading a number on the other pages, then three things that would be built differently if this were a live system rather than a study of a finished tournament.

What the data cannot answer
  • The sample is small. {{ totals.games }} games, {{ totals.players }} players and {{ totals.goals }} goals in the whole file, with {{ "{:,}".format(totals.shot_attempts) }} shot attempts to look at. Both xG models are fitted on the same {{ totals.training_goals }} goals - the ones scored at 5v5 in the international games. Read the shape of a map rather than its exact figures, and be careful about leaning on any single region.
  • A possession has a beginning, but no recorded end. The file marks where and when a player's possession starts - a Puck Recovery, a Reception or a Takeaway - but nothing necessarily marks where or when it ends.
    So possession time cannot be measured, and neither can carry distance.
  • There is no shift data. The file records how many skaters were on the ice for each event - that is where strength_state comes from, and it is what makes the 5v5 filtering on the other pages possible - but not who they were. Only the players directly involved in an event are ever named.
    That rules out on-ice analytics entirely. Anything of the form "how did this player's team do while he was on the ice" - on-ice corsi, on-ice expected goals, line combinations, deployment - cannot be built from this file, because the other skaters are anonymous.
What a production version would change

Everything above is a limit of the data. These are limits of how the project is put together, and all three would be answered differently for a system in daily use.

  • Where the data lives. The app reads one CSV. For a frozen tournament of this size that is the right call: it is simple, it travels with the code and there is nothing to run or pay for.
    A live system would keep the events in a database instead - for instance Postgres, either managed (e.g. Supabase, Neon, RDS) or on a server you control. That buys three things a file cannot. Indexes, so filtering hundreds of thousands of rows by team, player and strength state stays fast as the table grows. Concurrent access, so several analysts can query at once instead of passing a file around. And incremental writes, so a new game is an insert rather than a rewrite of the whole dataset.
    It would also move work into SQL. The slicers and the grouping behind every map are GROUP BY queries, and a database is better at those than pandas is.
  • How the data gets there. Today the pipeline is a script run by hand, which is fine for a dataset that never changes.
    If games arrived daily it would become a scheduled job: pull the new events, run the same cleaning steps, load them and refresh whatever is cached. GitHub Actions on a cron schedule is the cheapest way to start - a workflow that runs the pipeline on a timer and loads the result. A larger system would more likely run it on the server itself, so the load happens next to the database, but the shape is the same either way.
  • Who can see it. The current gate is one shared password. It answers "may this person look at all?" and nothing finer - everyone holding it sees everything, including the pages they have no use for.
    Real access would be per role, and the roles here are fairly obvious:
RoleWhat they would see
Players Their own numbers - a read-only view of their own shifts, shots and possession value. Not other players', and probably not the team-wide maps.
Coaches The whole team: every player, every situation, every page. This is the audience the site is built for.
Analysts Everything a coach sees, plus the pipeline: re-running the cleaning, adjusting the models and exporting the underlying data.

That needs real accounts rather than one password: a users table, hashed passwords, a session per visitor and a role check on each route. The useful part is that the code already draws that line in one place - every route goes through the same gate - so it is a change to the gate rather than to the pages.

None of this changes the analysis. The maps, the models and the rates would all be the same; what changes is where the data lives, how it gets there and who is allowed to see it.
